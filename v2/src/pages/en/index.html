One team from design to production

The people who design a system also build it and run it. Nothing gets lost in a hand-over, and nobody can say a problem belongs to someone else.

  1. Design

    We review what you have, name the risks, and put the proposed architecture and plan in writing before work starts.

    design-note.mdagreed before work starts

    • §1ProblemWhat has to change, and why
    • §2ConstraintsBudget, deadlines, the systems already in place
    • §3RisksNamed up front, each with a plan
    • §4DecisionArchitecture and plan, in writing

  2. Build

    Every change is tested and reviewed. Decisions are recorded where the next engineer will look for them.

    pipeline: mainevery change

    • ✓BuildFrom a clean checkout
    • ✓TestsAutomated, on every change
    • ✓ReviewApproved by a second engineer
    • ✓ReleaseSigned and versioned

  3. Run

    We monitor what we built, respond to incidents, and keep it patched and upgraded long after launch.

    runbook: productionafter launch

    • ●MonitoringMetrics, logs and traces
    • ●AlertsRouted to whoever is on call
    • ●RunbooksLinked from the alerts they answer
    • ●UpgradesPatched and scheduled, not postponed

Quality, in practice

“Because quality matters” is the principle Bixority was founded on. It covers every part of the work: the code, the infrastructure, how systems are operated and how we communicate.

Tested and reviewed
Changes ship after automated tests and a second pair of eyes, not before.
Open by default
We publish our tools and document what they do and what they don’t.
Built to recover
Systems are designed to fail safely and come back without heroics.
We question the plan
We ask awkward questions early. When a plan looks risky or wrong, we tell you directly, explain why and propose an alternative, because problems are cheapest to fix before anything is built.

Open-source tools

Eight projects, all written in Rust and published on GitHub and Codeberg.

All eight projects

github.com/bixoritycodeberg.org/bixority

  • object-storage-client

    One URL-based API for AWS S3, Google Cloud Storage, Azure Blob Storage, HTTP(S) and the local filesystem, as a Rust library, Python bindings, the osc command line and the osc-gui desktop browser.

    Product page Codeberg

  • pg-migrate

    Moves every user database and the global objects between two PostgreSQL servers in parallel, then checks row counts on both sides.

  • pg-maintenance

    Deletes rows older than a set number of days from PostgreSQL tables, in batches if needed.

  • object-storage-maintenance

    Streams old objects, such as audit logs, into a single compressed TAR archive.

  • amqp-bridge

    Forwards messages between two AMQP servers and reconnects on its own; also usable as a library with custom message transformers.
