DevOps and SRE

Platforms that are described in code, deployed by pipelines and looked after by the people who built them.

  • Kubernetes

    We design, build and operate clusters on your own hardware and on Amazon EKS, Azure AKS and Google GKE, and move workloads onto them.

    • On-premises clusters
    • Amazon EKS, Azure AKS and Google GKE
    • Cluster upgrades and workload migration
    • Helm charts and packaging

  • Infrastructure as code

    Every environment is described in code, reviewed like code and rebuilt from it, so no setup lives only in someone’s memory.

    • Terraform
    • Helm

  • CI/CD and release engineering

    Pipelines build, test, sign and package every release, so shipping is routine rather than an event.

    • Build and test pipelines
    • Signed releases
    • Container images and packages

  • Observability and incident response

    Monitoring that points at the cause, alerts worth acting on, and service level objectives agreed with you.

    • Metrics, logs and traces
    • Alerting and on-call
    • Service level objectives
    • Incident reviews

  • Database operations

    PostgreSQL migrations, backups and maintenance, using the same tools we publish as open source.

    • Migrations between servers
    • Backups and restore tests
    • Routine maintenance and data retention

Software development

From the first design document to maintenance years later, by the same team.

  • Architecture

    We start from the problem and its constraints, and write down the design, its trade-offs and its risks before any code is written.

  • Implementation

    We use the language that fits the job.

    • Rust for services and systems software
    • Python for services, automation and data tooling
    • TypeScript for web front ends

  • Testing and review

    Automated tests run on every change, and no change is merged without review.

  • Delivery and maintenance

    Releases go out through pipelines, with documentation. After launch we keep the software maintained: dependency updates, security fixes and new features.

Consulting

For when you need an outside view rather than a team.

  • Architecture and code reviews
  • Infrastructure assessments
  • A second opinion before a large technical decision

How an engagement starts

  1. Write to us

    Describe your system, what you want to change and any constraints. An email is enough to start.

  2. We study the current state

    We ask questions, read the documentation and code you can share, and talk to the people who run the system.

  3. You get a written proposal

    Scope, approach, risks and how we would work together, in writing, before you commit to anything.
